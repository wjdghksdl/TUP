# 🤝 TUP! - 공모전 팀 매칭 서비스 플랫폼

> **공모전 참가자를 위한 팀원 탐색 및 팀 빌딩 플랫폼**
>
> 공모전 참여 과정에서 발생하는 **팀원 탐색의 어려움과 비효율적인 팀 구성 문제**를 해결하기 위해 개발한 웹 기반 팀 매칭 서비스입니다.
> 사용자의 **역할, 보유 기술 및 역량, 공모전 참여 목적** 등을 바탕으로 적합한 팀원을 탐색할 수 있도록 하며,
> **AutoTeamUp**과 **OpenTeamUp** 두 가지 방식의 팀 구성을 지원합니다.

<br>

## 📌 Project Overview

### 💡 개발 배경

최근 기업의 채용 과정에서 실무 경험과 프로젝트 수행 경험을 중요하게 평가하면서, 대학생과 취업 준비생에게 공모전은 자신의 역량을 보여줄 수 있는 중요한 활동이 되었습니다.

하지만 팀 단위로 진행되는 공모전에 참여하기 위해서는 먼저 적절한 팀원을 찾아야 합니다.

기존의 팀원 모집 방식은 주로 커뮤니티나 게시판에 모집 글을 작성하고 사용자가 직접 여러 게시글과 지원자의 프로필을 확인하는 방식이기 때문에,

* 원하는 역할의 팀원을 찾는 데 많은 시간이 소요되고
* 지원자의 기술 및 역량을 일일이 확인해야 하며
* 팀 구성 이후에도 역할이나 역량의 불균형이 발생할 수 있다는

문제가 있습니다.

TUP!는 이러한 문제에 주목하여 **공모전 참가자가 자신의 역할과 역량을 등록하고, 필요한 팀원을 보다 효율적으로 탐색할 수 있는 팀 매칭 플랫폼**을 구현하는 것을 목표로 개발했습니다.

<br>

## 🎯 Project Goal

TUP!의 주요 목표는 다음과 같습니다.

1. **팀원 탐색 과정의 효율화**

   * 사용자의 역할과 기술 스택을 기반으로 필요한 팀원을 쉽게 검색
   * 다양한 조건을 활용한 팀원 탐색 지원

2. **다양한 팀 구성 방식 제공**

   * 시스템 기반의 팀원 탐색을 지원하는 `AutoTeamUp`
   * 팀장이 직접 팀원을 모집하고 선택하는 `OpenTeamUp`

3. **역량 기반의 팀 구성 지원**

   * 사용자의 역할 및 기술 스택을 활용하여 팀 구성에 필요한 정보를 구조화
   * 단순한 게시판 방식에서 벗어나 조건 기반의 팀원 탐색 지원

4. **팀 구성 이후의 협업까지 고려**

   * 팀원 간 피드백을 통해 협업 상태를 확인
   * 향후 피드백 데이터를 활용한 팀 리빌딩 및 추천 기능으로 확장할 수 있도록 설계

<br>

# ✨ Main Features

## 1. 🔍 AutoTeamUp

사용자가 원하는 공모전과 희망 역할을 선택하면 등록된 사용자 정보를 바탕으로 조건에 맞는 팀원을 탐색할 수 있는 기능입니다.

### 주요 기능

* 공모전별 팀원 탐색
* 희망 역할 기반 검색
* 기술 스택 및 역량 기반 필터링
* 조건에 맞는 사용자 목록 조회
* 매칭 요청 및 상태 관리

### 매칭 과정

```text
사용자 프로필 등록
        ↓
희망 역할 및 기술 스택 입력
        ↓
참여 공모전 선택
        ↓
조건에 맞는 사용자 탐색
        ↓
팀원 매칭 요청
        ↓
수락 / 거절
        ↓
팀 구성
```

초기 설계에서는 사용자의 역량과 활동 이력을 활용한 보다 고도화된 추천 방식을 고려했으며, 실제 구현에서는 프로젝트 일정과 구현 범위를 고려하여 **기술 스택 및 조건 기반의 탐색·필터링 방식**을 중심으로 구현했습니다.

향후 사용자 데이터가 충분히 축적될 경우 사용자 간 성향 및 협업 데이터를 활용한 추천 시스템으로 확장할 수 있도록 설계했습니다.

<br>

## 2. 👥 OpenTeamUp

팀장이 직접 팀을 생성하고 필요한 팀원을 모집할 수 있는 수동 팀 구성 방식입니다.

자동화된 매칭만으로 팀을 구성하기 어려운 경우 사용자가 직접 원하는 조건의 팀원을 선택할 수 있도록 하여 **사용자의 선택권을 보장**합니다.

### 주요 기능

* 팀 모집 게시글 작성
* 모집 역할 및 필요 역량 등록
* 팀원 검색
* 팀원 초대
* 팀원 지원
* 지원자 목록 확인
* 지원 승인 / 거절
* 팀 구성 및 관리

### 팀 구성 과정

```text
팀장
 ↓
팀 생성
 ↓
모집 조건 설정
 ├─ 모집 역할
 ├─ 필요 기술
 ├─ 모집 인원
 └─ 공모전 정보
 ↓
팀원 검색 / 지원
 ↓
지원자 확인
 ↓
승인 / 거절
 ↓
팀 구성
```

이를 통해 시스템이 제안하는 팀원뿐만 아니라 사용자가 직접 팀을 구성할 수 있는 **자율적인 팀 빌딩 환경**을 제공합니다.

## 3. 📝 Team Feedback

팀 구성 이후 팀원 간 협업 상태를 확인하기 위한 피드백 기능입니다.

팀 프로젝트에서는 팀을 구성하는 것뿐만 아니라 실제 협업 과정에서 발생하는 역할 수행, 의사소통 등의 문제가 중요하기 때문에 팀 구성 이후의 상태까지 고려할 수 있도록 설계했습니다.

### 피드백 항목

* 의사소통
* 업무 수행
* 협업 태도
* 전문성

각 항목을 기준으로 팀원 간 평가를 진행할 수 있도록 구성했습니다.

```text
팀 구성
  ↓
프로젝트 진행
  ↓
팀원 간 피드백
  ↓
협업 상태 확인
  ↓
팀 유지 / 리빌딩 판단
```

피드백 데이터는 향후 팀 리빌딩 및 추천 시스템을 고도화하는 데 활용할 수 있는 데이터로 확장할 수 있습니다.

<br>

---

## 4. 🔄 Team Rebuilding

팀 구성 이후 협업 과정에서 문제가 발생했을 경우 기존 팀을 그대로 유지하는 것뿐만 아니라 **팀 리빌딩을 고려할 수 있도록 설계**했습니다.

피드백 결과를 활용하여 팀의 협업 상태를 확인하고, 필요한 경우 새로운 팀 구성으로 이어질 수 있는 구조를 고려했습니다.

이를 통해 단순히 **"팀원을 찾아주는 서비스"**&#xC5D0; 그치지 않고,

> **팀 구성 → 협업 → 피드백 → 재구성**

으로 이어지는 팀 협업 구조를 목표로 했습니다.

# 🏗️ System Architecture

TUP!는 **Frontend - Backend - Database**를 분리한 구조로 개발했습니다.

```text
┌─────────────────────────────────────────────┐
│                  Client                     │
│                                             │
│              React Frontend                 │
│          SPA / UI / 사용자 입력              │
└──────────────────────┬──────────────────────┘
                       │
                       │ HTTP / JSON
                       ▼
┌─────────────────────────────────────────────┐
│                 Backend                     │
│                                             │
│        Django + Django REST Framework       │
│                                             │
│  ┌───────────┐ ┌───────────┐ ┌───────────┐ │
│  │   User    │ │   Team    │ │  Matching │ │
│  │   API     │ │   API     │ │   API     │ │
│  └───────────┘ └───────────┘ └───────────┘ │
│                                             │
└──────────────────────┬──────────────────────┘
                       │
                       │ ORM / SQL
                       ▼
┌─────────────────────────────────────────────┐
│                  Database                   │
│                                             │
│                  MySQL 8.0                  │
│                                             │
│   User / Team / Contest / Matching / ...   │
└─────────────────────────────────────────────┘
```

Frontend와 Backend는 REST API를 통해 통신하며, 서버에서 처리된 데이터는 JSON 형태로 클라이언트에 전달됩니다.

# 🗂️ Repository Structure

TUP!는 Frontend와 Backend를 하나의 Repository에서 관리하는 Monorepo 구조로 구성되어 있습니다.

```text
TUP/
├── backend/
│   ├── Dockerfile
│   ├── requirements.txt
│   ├── manage.py
│   └── ...
│
├── frontend/
│   ├── Dockerfile
│   ├── package.json
│   ├── public/
│   └── src/
│       └── ...
│
├── docker-compose.yml
├── .gitignore
├── LICENSE
└── README.md
```

### `/backend`

Django 기반의 서버 애플리케이션입니다.

* 사용자 관련 API
* 팀 관련 API
* 공모전 관련 API
* 매칭 요청 처리
* 데이터 조회 및 저장
* 데이터베이스 연동

등의 Backend 기능을 담당합니다.

### `/frontend`

React 기반의 Single Page Application입니다.

* 사용자 화면
* 공모전 탐색
* 팀원 탐색
* 팀 생성 및 모집
* 매칭 요청
* 사용자 프로필

등의 사용자 인터페이스를 담당합니다.

### `docker-compose.yml`

MySQL, Django Backend, React Frontend를 각각 컨테이너로 실행하고 서로 연결하기 위한 설정 파일입니다.

# 🗄️ Database Design

TUP!는 팀 매칭 서비스에서 발생하는 사용자, 팀, 공모전 및 매칭 관련 데이터를 관계형 데이터베이스로 관리합니다.

주요 데이터는 사용자와 팀을 중심으로 연결되며, 팀 구성 과정에서 발생하는 지원 및 매칭 상태를 관리할 수 있도록 설계했습니다.

### 주요 데이터 관계

```text
                    ┌─────────────┐
                    │    User     │
                    │             │
                    │ - profile   │
                    │ - skills    │
                    │ - role      │
                    └──────┬──────┘
                           │
                  ┌────────┼────────┐
                  │        │        │
                  ▼        ▼        ▼
              Team      Matching   Feedback
                  │       Request      │
                  │                    │
                  ▼                    ▼
               Contest              Team Member
```

### 데이터 설계 방향

#### User

사용자의 기본 정보와 역할, 보유 역량 및 기술 스택 등의 정보를 관리합니다.

#### Team

팀의 생성 정보와 팀장, 팀원 및 모집 상태 등의 정보를 관리합니다.

#### Contest

사용자가 참여하고자 하는 공모전 정보를 관리합니다.

#### Matching

사용자 간 팀원 매칭 요청 및 수락/거절 등의 상태를 관리합니다.

#### Feedback

팀 구성 이후 팀원 간 평가 정보를 저장하여 향후 팀 리빌딩 및 추천 기능에 활용할 수 있도록 구성합니다.

# 🔌 REST API

Frontend와 Backend는 RESTful API를 기반으로 통신하도록 구성했습니다.

주요 API 기능은 다음과 같습니다.

| Domain      | 기능             |
| ----------- | -------------- |
| User        | 사용자 등록 및 정보 조회 |
| Profile     | 프로필 및 기술 스택 관리 |
| Contest     | 공모전 조회 및 관리    |
| Team        | 팀 생성 및 팀 정보 관리 |
| Matching    | 팀원 검색 및 매칭 요청  |
| Application | 팀 지원 및 승인/거절   |
| Feedback    | 팀원 피드백 관리      |

API 요청과 응답은 JSON 형태로 처리하여 Frontend와 Backend의 역할을 명확하게 분리했습니다.

# 💻 Frontend

React를 기반으로 Single Page Application 구조를 적용하여 페이지 간 이동과 사용자 상태를 관리할 수 있도록 구성했습니다.

### 주요 화면

* 메인 페이지
* 공모전 목록
* 공모전 상세
* AutoTeamUp
* OpenTeamUp
* 팀 생성
* 팀원 모집
* 팀원 지원
* 마이페이지
* 팀 페이지
* 피드백

Frontend에서는 Axios를 활용하여 Backend REST API와 통신하며, React Router를 이용하여 화면 간 이동을 처리합니다.

또한 MUI를 활용하여 공통 UI Component와 Icon을 구성하고, CSS를 통해 서비스의 전체적인 화면 구성을 조정했습니다.

<br>

# ⚙️ Backend

Django와 Django REST Framework를 사용하여 RESTful API 서버를 구축했습니다.

Backend에서는 단순히 데이터를 전달하는 것뿐만 아니라 다음과 같은 서비스 로직을 처리합니다.

```text
Client Request
      ↓
Django REST API
      ↓
Request Validation
      ↓
Business Logic
      ↓
Database Query
      ↓
Response Data
      ↓
JSON Response
      ↓
React Client
```

이를 통해 Frontend와 데이터 저장 영역을 분리하고, 각 계층의 역할을 명확하게 구분했습니다.

<br>

# 🐳 Docker

개발 환경의 차이로 인해 발생할 수 있는 문제를 줄이고 Frontend, Backend, Database를 동일한 환경에서 실행하기 위해 Docker Compose를 사용했습니다.

현재 Compose 설정에서는 다음 세 개의 컨테이너를 사용합니다.

```text
┌─────────────────────┐
│   tup-frontend      │
│      React          │
│      :3000          │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│    tup-backend      │
│      Django         │
│      :8000          │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│     tup-mysql       │
│      MySQL 8.0      │
│      :3306          │
└─────────────────────┘
```

Docker Compose를 사용하면 각각의 개발 환경을 개별적으로 설정하지 않고 전체 서비스를 하나의 구성으로 실행할 수 있습니다.

# 🧩 Technical Challenges & Troubleshooting

## 1. 데이터 조회 성능 문제

팀원 탐색 과정에서는 여러 사용자의 정보를 조회하고 각 사용자의 기술 및 역할 정보를 함께 확인해야 하기 때문에 데이터 조회가 반복적으로 발생할 수 있습니다.

프로젝트 진행 과정에서 사용자 데이터 조회 과정에서 발생하는 쿼리 지연 문제를 확인하고 **데이터베이스 인덱스 및 조회 구조를 개선하여 평균 쿼리 처리 시간을 약 40% 단축**했습니다.

이를 통해 단순히 기능을 구현하는 것뿐만 아니라 실제 서비스에서 데이터 조회량이 증가했을 때 발생할 수 있는 성능 문제까지 고려했습니다.

<br>

## 2. Frontend ↔ Backend 데이터 불일치

Frontend에서 정상적으로 요청을 보내더라도 Backend에서 기대하는 데이터 구조와 실제 전달되는 데이터가 다르면 기능이 정상적으로 동작하지 않는 문제가 발생할 수 있었습니다.

이를 해결하기 위해 단순히 Frontend 또는 Backend 한쪽만 확인하는 것이 아니라,

```text
사용자 입력
   ↓
React State
   ↓
Axios Request
   ↓
Django API
   ↓
Request Data
   ↓
Business Logic
   ↓
Database
   ↓
Response
   ↓
React State
   ↓
UI
```

전체 데이터 흐름을 단계별로 확인하면서 문제의 원인을 추적했습니다.

이 과정에서 API 요청 데이터와 서버 응답 구조를 맞추고, Frontend에서 실제로 사용하는 데이터 형태까지 확인하면서 데이터 흐름을 기준으로 문제를 해결했습니다.

<br>

## 3. 기능 범위와 일정 조정

초기에는 자동화된 팀 매칭 기능을 보다 복잡한 추천 방식으로 구현하는 방향을 고려했지만, 프로젝트 일정과 구현 난이도를 함께 고려하여 핵심 서비스 기능에 우선순위를 두었습니다.

기존 REST API와 데이터 구조를 활용할 수 있는 기능은 최대한 재사용하고, 실제 서비스에서 핵심적인 **팀원 검색 및 조건 기반 매칭 기능을 우선 구현**했습니다.

이를 통해 제한된 프로젝트 기간 안에서 핵심 기능을 완성하는 것을 목표로 했습니다.

<br>

## 4. N+1 Query 문제에 대한 확장 고려

사용자와 기술 스택처럼 관계가 연결된 데이터를 한 번에 조회하는 과정에서는 데이터 규모가 증가할 경우 불필요한 추가 쿼리가 발생할 가능성이 있습니다.

현재 데모 규모에서는 큰 문제가 없지만 서비스가 확장될 경우 Django ORM의

```python
select_related()
prefetch_related()
```

등을 활용하여 관련 데이터 조회에 필요한 DB I/O를 줄이는 방향으로 개선할 수 있습니다.

사용자 성향 및 역량 분석

팀원 추천 점수 계산
